# تصمیم: مقدار `recipientId` در ارسال پیامک Arte → SmartX

## خلاصه برای اجرا

| مورد | مقدار |
|---|---|
| مشکل | `recipientId = 0` باعث می‌شود SmartX درخواست را Accept کند ولی `SmsMessages` ساخته نشود و پیامک به گوشی نرسد |
| قانون اسمارت | `recipientInfo[].recipientId` از نوع `long` و باید بزرگ‌تر از صفر باشد |
| تصمیم | گزینه **B** |
| قانون تولید | موبایل مشتری به‌صورت عدد `long`، بدون صفر اول؛ مثال: `09362660550` → `9362660550` |
| نیاز به تغییر PK مشتری Arte | خیر |

## مسئله در یک جمله

SmartX برای `direct-send` فیلد `recipientId` از نوع `long` و بزرگ‌تر از صفر می‌خواهد؛ Arte قبلاً همیشه `0` می‌فرستاد و به‌خاطر همین پیام Accept می‌شد ولی به اپراتور/گوشی نمی‌رسید.

## یافته فنی SmartX

- Endpoint: `POST https://api.smartx.ir/api/v1/notification/direct-send`
- فیلد: `recipientInfo[].recipientId` (`long`، اجباری `> 0`)
- اگر `recipientId <= 0` باشد:
  - HTTP معمولاً `204 Accepted` برمی‌گردد
  - ردیف `MessageBatches` ساخته می‌شود
  - ردیف `SmsMessages` ساخته نمی‌شود
  - پیامک به خط/گوشی نمی‌رود

### نمونه خراب (CASE-26)

```json
{
  "contactInfo": "989362660550",
  "body": "تعمیرگاه حکیمی\nلینک پیگیری ...",
  "recipientId": 0
}
```

### نمونه درست

```json
{
  "contactInfo": "989362660550",
  "body": "تعمیرگاه حکیمی\nلینک پیگیری ...",
  "recipientId": 9362660550
}
```

## اسمارت از `recipientId` چه استفاده‌ای می‌کند؟

| سؤال | جواب |
|---|---|
| برای چه استفاده می‌شود؟ | ذخیره روی پیام (`SmsMessages`) و اعتبارسنجی ساخت پیام؛ برای consent اصلی نیست |
| Consent / رضایت پیامکی؟ | با شماره موبایل + Provider چک می‌شود، نه با `recipientId` |
| باید پایدار per مشتری باشد؟ | برای ارسال کافی است فقط `> 0`؛ برای ردیابی بهتر، پایدار per مشتری توصیه می‌شود |
| تداخل با شناسه‌های داخلی SmartX؟ | برای این مسیر مهم نیست؛ هر `long` مثبت خارجی قابل قبول است |
| فرمت خاص؟ | فقط `long > 0`؛ یکتایی سراسری اجباری اعلام نشده |

## تصمیم نهایی

- `recipientId` باید: `> 0`؛ ترجیحاً پایدار per مشتری
- تداخل با شناسه‌های داخلی اسمارت: مهم نیست
- انتخاب: **B**
- قانون دقیق: رقم‌های موبایل ایرانی بدون صفر اول  
  - `09362660550` → `9362660550`  
  - `989362660550` → `9362660550`

پیاده‌سازی Arte: `Mobile.TryToNationalLong` + اعمال در `SmartXSmsClient` هنگام ساخت payload (حتی اگر caller مقدار `0` بدهد، بازنویسی می‌شود).

## گزینه‌هایی که رد شدند

| گزینه | وضعیت | دلیل |
|---|---|---|
| A — مقدار ثابت `1` برای همه | فقط اضطراری کوتاه‌مدت | ارسال را راه می‌اندازد، ولی همه گیرنده‌ها یکی دیده می‌شوند |
| C — ترکیب آی‌دی عددی + موبایل | رد | در Arte مشتری Guid است؛ عدد ترتیبی آماده نیست |
| D — عوض کردن PK به long | رد | هزینه خیلی بالا برای یک فیلد |
| E — ستون long جدا | لازم نیست الان | فقط اگر بعداً ردیابی پیشرفته بخواهید |
| F — hash از Guid | جایگزین قابل قبول | اگر موبایل در دسترس نبود؛ الان لازم نیست |

## معیار موفقیت

بعد از تغییر، برای یک ارسال تستی:

- `MessageBatches` ساخته شود
- `COUNT(SmsMessages WHERE BatchId = …) = 1`
- در صورت سلامت خط/اپراتور، وضعیت پیام به Sent/Delivered برسد

برای تأیید سمت SmartX بفرستید: `correlationId`، زمان ارسال، شماره گیرنده.

## تماس‌های API (مرجع)

1. توکن: `POST /connect/token` با `grant_type=tenant_service`
2. ارسال: `POST /api/v1/notification/direct-send`  
   فیلد: `recipientInfo[].recipientId` (`long`، باید `> 0`)
