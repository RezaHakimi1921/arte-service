# پلن توسعه Arte Service — ماژول موتورسازی (مکانیک موتور)

> پروژه: arte-service (ASP.NET Core + React PWA)
> وضعیت: همه‌ی موارد انجام‌شده در `main` هستند و روی سرور production دیپلوی شده‌اند (health check سالم). جدول وضعیت پایین را ببینید.

## فاز 1A — پایه‌ها

### 1. نهایی‌سازی سیستم پیامک (در حال انجام)
- تکمیل کار جاری؛ بازه‌ی ارسال 08:00 تا 23:00 برای همه‌ی پیامک‌ها
- تعریف **رویدادهای پیامک** به‌صورت یک جدول/enum مرکزی (پذیرش، منتظر قطعه، آماده تحویل، تحویل، نظرسنجی، …) تا تنظیمات روشن/خاموش بعدی (موارد 7 و 13) روی همین بنا شود
- لاگ ارسال + وضعیت تحویل

### 10. باگ: تخفیف فاکتور در لینک مشتری نمایش داده نمی‌شود
- نمایش «تخفیف شما: X تومان» در صفحه‌ی لینک/فاکتور مشتری
- بررسی اینکه DTO لینک مشتری فیلد تخفیف را برمی‌گرداند و مبلغ نهایی = جمع − تخفیف

### 11. باگ: کالای «منتظر قطعه» سود را صفر نشان می‌دهد
- سود باید از قیمت خرید/فروش محاسبه شود، نه از وضعیت کالا
- وضعیت «منتظر قطعه» فقط روی موجودی/گردش کار اثر دارد، نه روی سود (به ADR قبلی `AffectsInventory()` و `RequiresWorkflow` توجه شود)
- تست واحد برای محاسبه‌ی سود در هر وضعیت

### 12. تاریخچه: ثبت «چه کسی» هر مرحله را انجام داده
- جدول `CaseHistory` (یا `AuditLog` اختصاصی پرونده): `CaseId`, `Action/Status`, `UserId`, `At`, `Note`
- نمایش نام کاربر کنار هر مرحله در تایم‌لاین پرونده
- این جدول منبع گزارش عملکرد (فاز 1E) و پوش (1D) هم هست

### 15. سطح دسترسی (نقش‌ها)
| نقش | دسترسی |
|---|---|
| مدیر | همه‌چیز + همه‌ی تنظیمات |
| مکانیک ارشد | تایید، دیدن همه‌ی فروش‌ها و دخل‌وخرج، فقط گزارش‌ها؛ **بدون** دسترسی به تنظیمات |
| مکانیک | پذیرش و ثبت تا مرحله‌ی «تایید به استاد»؛ انجام کار |
| کارآموز | فقط مشاهده‌ی پنل؛ هیچ تغییری ممکن نیست (read-only) |

- پیاده‌سازی با **Permission/Policy** (نه چک مستقیم نقش) تا بعداً با تیم‌بندی و سفارشی‌سازی راحت‌تر شود
- اعمال در بک‌اند (Authorization policies) و مخفی‌کردن UI در فرانت
- تست: هر نقش × هر endpoint حساس

### 18. مدیریت کاربران و رمز عبور در پنل
- ساخت کاربر جدید (نام کاربری + رمز عبور + نقش) از داخل پنل
- تغییر نام کاربری و رمز عبور از داخل پنل، برای **هر نقش**:
  - هر کاربر (با هر نقشی) رمز خودش را تغییر دهد (با وارد کردن رمز فعلی)
  - مدیر بتواند برای همه‌ی کاربران رمز را ریست/تغییر دهد
- رمز به‌صورت hash ذخیره شود؛ حداقل پیچیدگی؛ ثبت تغییر در تاریخچه/لاگ
- نیازمند تایید: آیا مکانیک ارشد هم اجازه‌ی ساخت/ریست رمز کاربران زیرمجموعه را دارد؟ (فعلاً فقط مدیر)

### 19. باگ: نصب PWA روی تبلت قدیمی خطا می‌دهد
- خطا: `this device does not support rotation vector sensor`
- مسیر بررسی:
  1. مشخص کردن نسخه‌ی اندروید/مرورگر/WebView تبلت و اینکه خطا هنگام نصب است یا هنگام اجرا
  2. جست‌وجو در کد فرانت و manifest برای استفاده از Sensor/DeviceOrientation/Generic Sensor API یا کتابخانه‌ای که از آن استفاده می‌کند (مثلاً اسکنر، نقشه، گالری، چرخش تصویر)
  3. بررسی فیلد `orientation` در `manifest.json` (در صورت قفل‌کردن جهت، حذف یا استفاده از مقدار `any`)
- راه‌حل: feature detection (`'AbsoluteOrientationSensor' in window`) + try/catch دور هر استفاده از سنسور، و عدم وابستگی هیچ بخش حیاتی به سنسور
- راه‌حل جایگزین برای دستگاه‌های قدیمی: اجرای عادی در مرورگر یا «Add to Home Screen» بدون WebAPK
- تست روی تبلت واقعی یا شبیه‌ساز اندروید قدیمی

## فاز 1B — هسته‌ی پذیرش

### 2. دسته‌بندی ایرادات و خدمات + چک‌لیست پذیرش

**جریان کار:** مشتری ایراد/درخواست اعلام می‌کند ← پذیرش‌کننده نوع موتور را انتخاب می‌کند (دنده‌ای / اتوماتیک-کلیک) ← چک‌لیست مربوط بارگذاری می‌شود و همه‌ی گزینه‌ها بررسی می‌شوند.

**الف) کاتالوگ ایرادات و خدمات (در تنظیمات)**
- کاربر خودش آیتم اضافه/ویرایش/غیرفعال کند (بدون نیاز به تایپ هر بار)
- در پذیرش از لیست انتخاب شود (+ امکان افزودن سریع آیتم جدید)

**ب) نوع موتور**
- فیلد `MotorType` روی وسیله: `Geared` (دنده‌ای) / `Automatic` (کلیک/اتوماتیک)

**ج) قالب چک‌لیست (در تنظیمات)**
- دو قالب جدا: چک‌لیست موتور دنده‌ای، چک‌لیست موتور اتوماتیک
- هر سطر: عنوان، ترتیب، **الزامی بودن**، فعال/غیرفعال
- ویرایش، افزودن، حذف (soft delete) و جابه‌جایی ترتیب
- تعداد آیتم‌ها ممکن است ~30 باشد ← UI سریع و لمسی (PWA)، دسته‌بندی بخش‌ها (موتور، ترمز، برق، …) اختیاری

**د) چک‌لیست در پذیرش**
- بعد از «موارد اعلامی مشتری» نمایش داده می‌شود
- با انتخاب نوع موتور، قالب مربوط **snapshot** می‌شود در پرونده (تا تغییر بعدی قالب، پرونده‌های قدیمی را خراب نکند)
- آیتم‌های الزامی تیک نخورند ← پذیرش نهایی نشود
- مدل داده (پیشنهادی):
  - `ChecklistTemplate` (Id, MotorType, Name)
  - `ChecklistTemplateItem` (TemplateId, Title, IsRequired, Order, IsActive)
  - `CaseChecklistItem` (CaseId, Title, IsRequired, IsChecked, CheckedBy, CheckedAt, Note)

### 17. ثبت دائمی ایرادات اعلامی/کشف‌شده
- دو نوع ایراد: **اعلامی توسط مشتری** و **کشف‌شده توسط مکانیک**
- همیشه قابل ثبت (حتی در میانه‌ی کار) و ذخیره با ارجاع به کاتالوگ ایرادات (2-الف)
- هدف: داده‌ی قابل تحلیل (پرتکرارترین ایرادات به تفکیک مدل موتور/ماه) برای گزارش‌های بعدی

## فاز 1C — مالی و لینک مشتری

### 3. بارگذاری رسید پرداخت توسط مشتری + الزام پرداخت
- در لینک مشتری، آپلود عکس رسید (محدودیت حجم/نوع، فشرده‌سازی سمت کلاینت)
- وضعیت رسید: در انتظار تایید ← تایید/رد توسط مکانیک ارشد/مدیر
- **تنظیم اختیاری:** «شروع کار / تهیه قطعه منوط به پرداخت مشتری باشد» (روشن/خاموش در تنظیمات)
  - در صورت روشن بودن، تغییر وضعیت به «شروع کار/خرید قطعه» بدون پرداخت تاییدشده مسدود شود

### 14. مالی: کارتخوان‌ها و کارت‌ها
- بخش «مالی» در تنظیمات (یا زیرمجموعه‌ی اطلاعات کسب‌وکار):
  - **انواع کارتخوان** (نام، بانک، فعال/غیرفعال) ← هنگام ثبت پرداخت، انتخاب کارتخوان
  - **کارت‌ها** (شماره کارت، نام صاحب حساب، بانک) برای کارت‌به‌کارت
  - انتخاب «کارت نمایشی در لینک مشتری»
- در لینک مشتری: نمایش کارت انتخاب‌شده با **دکمه‌ی کپی**
- ثبت پرداخت: روش (نقدی / کارتخوان / کارت‌به‌کارت) + کارتخوان/کارت مبدأ

### 5. شماره تماس در لینک مشتری
- در اطلاعات کسب‌وکار: شماره تماس قابل ویرایش + **سوییچ نمایش/عدم نمایش** در لینک

### 6. اینستاگرام و لوکیشن‌ها
- اطلاعات کسب‌وکار: آیدی اینستاگرام + لینک **نشان، گوگل‌مپ، ویز، (و یک مورد دیگر)** — ۴ برنامه‌ی نقشه/مسیریابی
- لینک مشتری: بخش جمع‌وجور و **تب‌شکل** برای لوکیشن‌ها (فقط مواردی که پر شده‌اند) + آیکن اینستاگرام در انتهای صفحه
- **نکته‌ی طراحی:** نظرسنجی هم در همین صفحه است؛ این بخش‌ها باید کم‌حجم و پایین صفحه باشند تا صفحه شلوغ نشود

## فاز 1D — اعلان‌ها و تنظیمات اتوماسیون

### 7. پیامک «منتظر قطعه» (تنظیمات)
- سوییچ: هنگام ثبت وضعیت «منتظر قطعه از مشتری»، پیامک به مشتری ارسال شود یا نه

### 13. پیامک به استاد هنگام «پایان کار» شاگرد
- سوییچ در تنظیمات؛ وقتی کارآموز/مکانیک وضعیت را «تمام شد» می‌زند، به استاد (مکانیک ارشد مسئول) پیامک برود تا بررسی کند

> هر دو روی سیستم رویداد/تنظیمات پیامک مرحله‌ی 1A ساخته می‌شوند: `SmsEventSetting(Event, IsEnabled, Recipient)`

### 8. Push Notification (PWA)
- Web Push (VAPID) + ثبت Subscription هر کاربر/دستگاه
- رویدادهای مهم: شروع کار، پایان کار، تحویل، ثبت نظر مشتری، (رسید پرداخت جدید)
- گیرنده بر اساس نقش (مثلاً استاد برای «پایان کار»)
- محدودیت: iOS فقط برای PWA نصب‌شده روی Home Screen؛ در نظر گرفتن این در UX

### 4. فیلم علاوه بر عکس
- ضبط/آپلود ویدیو با **فشرده‌سازی سمت کلاینت** (محدودیت مدت و رزولوشن) برای کاهش حجم
- ذخیره‌سازی: تعیین محل (دیسک سرور / Object Storage) و سیاست نگهداری (مثلاً حذف پس از N ماه)
- حدس ریسک: فضای VPS؛ پیشنهاد کوتاه نگه داشتن مدت و رزولوشن پایین
