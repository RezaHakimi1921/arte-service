# 15 — پیامک از مسیر اسمارت‌ایکس

**وضعیت:** کلاینت (فاز ۱)، آداپتر Provider، مخزن شارژ، متن پیامک هر شعبه و پنل ادمین پیاده شده است. تا وقتی `Sms:Provider=smartx` (یا `SMARTX_KEYS`) تنظیم نشود، ارسال روی پنل قبلی می‌ماند و رفتار برنامه عوض نمی‌شود.

## تصمیم‌ها

- Arte فقط لوله‌ی ارسال به اسمارت است (`POST /connect/token`، `POST /api/v1/notification/direct-send`). صف، وضعیت تحویل، موجودی شعبه و انتخاب خط پیاده نشده‌اند.
- **کد ورود (`auth.otp`) هرگز از اسمارت نمی‌رود.** همیشه از `Sms:Provider` (Faraz / Iran Payamak) فرستاده می‌شود و هزینه‌اش روی Arte می‌ماند؛ از شارژ هیچ شعبه‌ای کم نمی‌شود.
- بقیه‌ی پیام‌ها (`case.*`، `survey.request`، …) با `SMARTX_ALL=true` از اسمارت می‌روند و هزینه‌شان از **شارژ همان شعبه** کم می‌شود؛ موجودی مرکزی هم با هر پارت کم می‌شود.
- قیمت هر پارت: خرید ۱۰۰ تومان، فروش ۲۱۹ تومان (قابل تغییر در پنل ادمین، نه در کد).
- همه‌ی پیام‌ها غیر از کد ورود فقط ۰۸:۰۰ تا ۲۳:۰۰ به وقت تهران فرستاده می‌شوند (`SmartXSms__SendFromHour/SendUntilHour`). بیرون از این بازه پیام فرستاده **نمی‌شود** (در تاریخچه‌ی پرونده با دلیل ثبت می‌شود)؛ نظرسنجی خودش تا صبح صبر می‌کند. پیام تأخیری/صف ساخته نشده است.

## تنظیمات (`deploy/.env`)

| نام | توضیح |
|---|---|
| `SMS_PROVIDER` | همیشه `iranpayamak` (Faraz): کد ورود از این سرویس می‌رود و هرگز از اسمارت نمی‌رود |
| `SMARTX_ALL` | `true`: همه‌ی پیام‌ها غیر از کد ورود از اسمارت. پیش‌فرض `false` |
| `SMARTX_KEYS` | برای آزمایش تک‌تک: با ویرگول، مثلاً `case.opened`. با `SMARTX_ALL` همزمان نباشد؛ `auth.otp` نباید در آن باشد |
| `SMARTX_BASE_URL` | staging: `https://staging-api.smartx.ir` ، production: `https://api.smartx.ir` |
| `SMARTX_CLIENT_ID` / `SMARTX_CLIENT_SECRET` / `SMARTX_TENANT_ID` | از بک‌آفیس اسمارت؛ فقط روی سرور |
| `SMARTX_SENDER_NUMBER` | خط ثابت ارسال |
| `SMARTX_REQUIRE_APPROVED` | `true`: فقط متن تأییدشده‌ی شعبه فرستاده شود؛ پیش‌فرض `false`: تا تأیید، متن سیستم |

اگر `SMARTX_ALL=true` یا `SMARTX_KEYS` پر باشد و یکی از مقدارهای SmartX خالی باشد، برنامه بالا نمی‌آید و نام کلید گمشده را می‌گوید. `Sms:Provider=smartx` و `smsir` پذیرفته نمی‌شوند.

## مخزن شارژ

واحد همه‌چیز **پارت** است. دو سطح:

- **دفتر مرکزی:** آنچه در پنل اسمارت داریم (ثبت دستی تا وقتی اسمارت API موجودی بدهد).
- **شارژ هر شعبه:** ادمین دستی می‌دهد.

قوانین (فقط در `SmsWalletService`):

1. مجموع شارژ شعبه‌ها هیچ‌وقت از موجودی مرکزی بیشتر نمی‌شود؛ شارژ دادن بیشتر از «آزاد»، با پیام فارسی رد می‌شود. (اگر موجودی مرکزی را پایین‌تر ثبت کنید، هشدار قرمز می‌آید.)
2. پیام شعبه هم از شعبه و هم از مرکزی کم می‌کند.
3. شعبه‌ای که پارت کافی ندارد رد می‌شود (`insufficient_credit`) و در تاریخچه‌ی پرونده می‌آید.
4. کسر با یک `UPDATE` شرطی انجام می‌شود، پس دو پیام هم‌زمان یک پارت را دو بار خرج نمی‌کنند.
5. پیامی که اسمارت نپذیرفت، پارت‌هایش را برمی‌گرداند. «پذیرفته» یعنی اسمارت قبول کرد، نه رسیدن به گوشی.
6. هر تغییر در `SmsLedger` (فقط‌افزودنی) ثبت می‌شود.

تعداد پارت **تخمین** است: فارسی (UCS-2) ۷۰ نویسه برای یک پارت و بعد ۶۷؛ لاتین ۱۶۰ و بعد ۱۵۳. شمارش واقعی شاتل هنوز از اسمارت تأیید نشده.

پنل ادمین ← «پیامک و شارژ»: موجودی مرکزی، ثبت خرید از اسمارت، ثبت موجودی پنل، قیمت‌ها، فهرست شعبه‌ها. صفحه‌ی هر کسب‌وکار ← بخش «پیامک»: شارژ دستی (با پارت یا با مبلغ؛ مبلغ ÷ قیمت فروش) و متن‌ها. مالک شعبه شارژ خودش را در `GET /api/v1/sms/wallet` می‌بیند.

دستور سرور (همان قوانین):

```bash
docker compose run --rm -T api sms-wallet show
docker compose run --rm -T api sms-wallet central-sync 100            # موجودی پنل اسمارت (پارت)
docker compose run --rm -T api sms-wallet credit "مکانیک موتور" 100    # نام یا شناسه‌ی شعبه
```

(`CustomerId = 12` در دیتابیس قدیمی SQL Server بود؛ در Arte هر شعبه یک `Tenant` با شناسه‌ی Guid است و با نام پیدا می‌شود.)

## متن پیامک هر شعبه

برای هر `(شعبه، MessageKey)`: پیش‌نویس ← تأیید ادمین ← ارسال. متن تأییدشده‌ی همان شعبه فرستاده می‌شود، وگرنه متن سیستم (`SmsTemplates.Branch`). تگ‌ها: `{{CustomerName}}`، `{{CustomerLink}}`، `{{WorkshopName}}`، `{{CaseCode}}`، `{{Vehicle}}`. متن تا ۴۰۰ نویسه؛ پیام‌های دارای لینک باید `{{CustomerLink}}` داشته باشند. تاریخ و کاربر تأیید ثبت می‌شود. متن کد ورود سراسری است (Faraz) و هزینه‌اش با Arte.

## کلاینت

کد در `src/Arte.Api/Sms/SmartX/`. هر بچ (حداکثر ۱۰۰ گیرنده) یک UUID (`correlationId`) دارد که قبل از ارسال ثبت می‌شود و روی timeout/۵xx/۴۲۹ با همان UUID دوباره فرستاده می‌شود؛ `401` یک بار با توکن تازه؛ سایر ۴xx دائمی. اگر تلاش‌ها تمام شود بچ `Pending` می‌ماند. روی `HttpClient` اسمارت باید `User-Agent` غیرخالی باشد؛ nginx اسمارت بدون آن `403 Forbidden` برمی‌گرداند.

## محدودیت‌ها و کارهای بعدی

- `ISmsBatchLog` فقط در حافظه است؛ با ری‌استارت، بچ‌های `Pending` از دست می‌روند (پیامی که تلاش‌هایش تمام شد به‌عنوان ناموفق حساب و پارتش برگردانده می‌شود). ذخیره‌ی پایدار نیاز به entity و migration جدا دارد.
- وضعیت تحویل، موجودی خودکار شعبه‌ی Arte از اسمارت و خط تبلیغاتی (لغو ۱۱) هنوز ساخته نشده‌اند.
- بی‌پاسخ از اسمارت: رفتار کمبود اعتبار، تکرار `correlationId`، سقف/نرخ، شمارش پارت شاتل، قرارداد فروش مجدد.

## راه‌اندازی و تست

1. مقدارهای بالا را در `deploy/.env` بگذار (staging).
2. `SMS_PROVIDER=iranpayamak` را نگه دار و `docker compose up -d` بزن.
3. تست مستقیم: `docker compose run --rm -T api smartx-test <موبایل>` ← باید `Accepted by SmartX` بگوید و پیامک برسد.
4. موجودی مرکزی و شارژ شعبه را ثبت کن، بعد `SMARTX_KEYS=case.opened` را بگذار و یک پرونده‌ی تست باز کن. اگر درست بود، `SMARTX_KEYS` را خالی کن و `SMARTX_ALL=true` بگذار.
