# ۲۸ — فلو پذیرش و نگاشت پیشنهادی خدمت→نوع درخواست

**وضعیت:** فلو + برش اول **قطعی**؛ **نگاشت خدمت→نوع تعویق (گزینهٔ D)** — جدول بخش ۳ وارد کد نشود.  
**اولویت / مرجع مسیر:**  
`مشتری و وسیله (یک صفحه) ← شرح پذیرش (کارت نوع → جزئیات) ← بازبینی (تخصیص و ثبت)`  
**قفل مالک ۱۴۰۵/۰۹/۰۴:** استپر بیرونی سه‌مرحله‌ای؛ S2=**D**؛ S1 جدول تأیید نشد؛ S4 همان رسانهٔ پذیرش؛ A=نوع کافی برای ثبت (ایراد/خدمت اجباری نیست)؛ B=پروندهٔ بی‌نوع → سایر (قبلی).  
**کد امروز:** استپر ۳تایی هست؛ کارت→جزئیات نیست. سرور هنوز بدون ایراد/خدمت/شرح، create را رد می‌کند — در برش اول باید با تصمیم A هم‌خوان شود (تغییر کوچک اعتبارسنجی؛ توضیح در PR کد).  
**تاریخ:** ۱۴۰۵/۰۹/۰۲؛ قفل مسیر و D/A/S۴–۶ در ۱۴۰۵/۰۹/۰۴.

## ۱. قطعی در برابر در انتظار تأیید

### ۱.۱ قطعی (مالک تأیید کرده — حفظ شود)

| موضوع | تصمیم |
|---|---|
| چهار نوع سطح‌بالا | `wrenching` آچارکشی · `diagnosis` عیب‌یابی · `repair` درخواست فنی/تعمیرات · `other` سایر |
| چندنوع در یک پرونده | مجاز |
| تعویض چرخ | زیر «سایر»، نه نوع سطح‌بالا |
| ایراد اعلامی مشتری | جدا از خدمات درخواستی و جدا از تشخیص فنی تعمیرکار (`Diagnosis`) |
| ایراد اعلامی و عیب‌یابی | ایراد اعلامی مشتری در جزئیات عیب‌یابی **حفظ** می‌شود (گفتهٔ مشتری)؛ نتیجهٔ فنی عیب‌یابی بعد از ثبت روی پرونده ثبت می‌شود و با ایراد اعلامی یکی نیست |
| چک‌لیست | فقط برای سه نوع اول در صورت نگاشت تنظیمات؛ «سایر» بدون چک‌لیست اجباری |
| زمان چک‌لیست | پس از ثبت پرونده روی صفحهٔ پرونده؛ ناقص‌بودن مانع ایجاد پرونده نیست، مانع شروع کار است |
| نگاشت چک‌لیست | سمت سرور (`RequestTypeChecklistBinding`) — از قبل پیاده شده |
| پیش‌نویس، برگشت مراحل، عکس/فیلم، مسئول، خلاصهٔ بازبینی | حفظ |
| استپر بیرونی پذیرش | **سه مرحله:** ۱) مشتری و وسیله با هم · ۲) شرح پذیرش · ۳) بازبینی |
| داخل «شرح پذیرش» | ابتدا **چهار کارت** چندانتخابی؛ انتخاب کارت **خودکار** جلو نمی‌رود؛ با «ادامه» وارد **جزئیات** می‌شود |
| جزئیات (برش اول / D) | بلوک‌های مرتبط با نوع (ایراد، شرح، …) مرتب و روشن؛ **فهرست خدمات هنوز فقط بر اساس نوع وسیله** — وابسته به کارت نوع نشود |
| «سایر» در جزئیات | شرح آزاد + همان عکس/فیلم پذیرش (پیوست جدا نه)؛ **پیوست شرط ثبت نیست** |
| نگاشت خدمت→نوع | **تعویق (D)**؛ جدول بخش ۳ و ردیف‌های مبهم وارد کد/API/مدل نشوند |
| S1 | جدول نگاشت **تأیید نشد**؛ کل نگاشت عقب افتاد |
| S2 | **D** انتخاب شد |
| S3 (برای فاز نگاشت آینده) | بله، یک خدمت می‌تواند زیر چند نوع باشد؛ در UI یک‌بار بدون تکرار |
| S4 | همان رسانهٔ پذیرش کافی است |
| S5 (فاز نگاشت آینده) | فهرست ترکیبی بدون تکرار؛ تا آن فاز = فهرست فعلی بر اساس نوع وسیله |
| S6 | خدمات سفارشی tenant **بعداً**؛ تنظیمات/API تازه الان نه |
| A — ثبت بدون «سایر» | ایراد/خدمت با آچارکشی، عیب‌یابی یا تعمیر **مجاز** است؛ برای create وجود **حداقل یک نوع درخواست کافی** است و خالی بودن ایراد/خدمت نباید ثبت را مسدود کند |
| B — پروندهٔ بی‌نوع | مثل قبل: مؤثر/نمایش «سایر»؛ تصمیم تازه لازم نیست |

### ۱.۲ هنوز باز / خارج از برش اول

| موضوع | وضعیت |
|---|---|
| تأیید نهایی جدول بخش ۳ و ردیف‌های ؟ برای اعمال در محصول | **عقب‌افتاده**؛ بخش ۳.۴ فقط بایگانی پیشنهاد مالک برای آینده است، نه مجوز کد |
| شکل فنی A/B/C وقتی نگاشت از تعویق خارج شد | بعد از برداشتن D |
| قیمت تحویل، گیرندهٔ SMS، صف پیامک، مرز نظرسنجی، … | اسناد دیگر؛ خارج از برش فلو |

### ۱.۳ وضعیت کد امروز (واقعیت، نه هدف)

روی `main` `84da1b9`:

- استپر بیرونی **۳**تایی هست (مشتری+وسیله → شرح → بازبینی) — با هدف جدید هم‌خوان است.
- شکاف اصلی: داخل شرح پذیرش هنوز **یک صفحهٔ تخت** است (چیپ نوع + ایراد + خدمت + عکس با هم)؛ زیرمرحلهٔ کارت→جزئیات و پنهان‌کردن بلوک نامرتبط **نیست**.
- خدمات فقط با نوع وسیله؛ جدول بخش ۳ اعمال نشده (و نباید تا تأیید مالک).

## ۲. فلو هدف (قطعی برای مشخصات)

```text
[1 مشتری و وسیله] → [2 شرح پذیرش] → [3 بازبینی / تخصیص و ثبت]
                           │
                           ├─ 2a چهار کارت نوع (چندانتخابی) + ادامه
                           └─ 2b جزئیات فقط برای نوع‌های انتخاب‌شده
```

### مرحله ۱ — مشتری و وسیله (یک صفحه)
جستجوی مشتری (موبایل / پلاک)، مشتری جدید یا قبلی؛ سپس وسیلهٔ همان مشتری (موجود یا ثبت تازه). نوع وسیله طبق کسب‌وکار؛ جزئیات اختیاری (رنگ، VIN، …) جمع‌شونده تا صفحه شلوغ نشود. پلاک اختیاری.

### مرحله ۲ — شرح پذیرش
1. **کارت‌ها:** آچارکشی، عیب‌یابی، درخواست فنی/تعمیرات، سایر — چندانتخابی؛ حداقل یک نوع برای «ادامه». لمس کارت صفحه را عوض نمی‌کند.
2. **جزئیات (پس از ادامه):** بلوک‌ها مرتب بر اساس نوع‌های انتخاب‌شده:
   - آچارکشی / تعمیرات: ایراد اعلامی مشتری (+ فهرست خدمات فعلی بر اساس **نوع وسیله**، نه نگاشت نوع‌درخواست)
   - عیب‌یابی: **ایراد اعلامی مشتری حفظ**؛ نتیجهٔ فنی/`Diagnosis` اینجا ثبت نمی‌شود
   - سایر: شرح آزاد؛ همان انتخابگر عکس/فیلم؛ بدون چک‌لیست اجباری
   - چند نوع: اجتماع بلوک‌ها بدون تکرار بی‌مورد؛ خدمات هنوز یک فهرست وسیله‌محور
3. عکس/فیلم اختیاری؛ آپلود بعد از create؛ شرط ثبت نیست. چک‌لیست فقط بعد از ثبت روی پرونده.

### مرحله ۳ — بازبینی
خلاصهٔ مشتری، وسیله، نوع‌ها، جزئیات، تعداد رسانه؛ **اختصاص مسئول**؛ تیک پیامک پذیرش؛ سوخت/بدنهٔ اختیاری؛ ثبت پرونده.

### ۳.۳ قواعد پیشنهادی برای اعمال جدول (فقط وقتی نگاشت از D خارج شد)

1. فیلتر نهایی = اشتراک (نوع وسیله ∩ اتحاد نوع‌های انتخاب‌شده).  
2. خدمت فقط-O فقط با «سایر».  
3. خدمت چندنوعی اگر هر کدام از نوع‌ها انتخاب شده دیده شود؛ در UI یک‌بار.  
4. تا خروج از D این قواعد در کد اعمال نشوند.

### ۳.۴ بایگانی پیشنهاد مالک برای ردیف‌های مبهم (۱۴۰۵/۰۹/۰۴) — نه مجوز کد

| مورد | پیشنهاد آینده (W سرویس/تنظیم · D عیب‌یابی · R تعمیر · O سایر) |
|---|---|
| تنظیم انژکتور | W؛ اگر پیدا کردن علت = D؛ اگر تعمیر قطعه = R |
| روغن ترمز | W؛ نشتی ترمز = R |
| تنظیم فرمان / بالانس چرخ / روغن گیربکس | W |
| باتری | فعلاً نگاشت نشود؛ تست = D، تعویض/تعمیر = R، شارژ = خدمت جدا |
| شارژ گاز کولر | W؛ نشتی کولر = R |
| تعمیر رینگ | R |
| کاربراتور / CVT | تنظیم یا سرویس = W؛ عیب‌یابی = D؛ تعمیر = R |
| ترمز کفشکی | R |
| چراغ، قاب، پره | تعمیر/تعویض = R؛ عیب‌یابی برقی = D |

بازبینی نام واقعی خدمت قبل از هر قفل آینده لازم است.
