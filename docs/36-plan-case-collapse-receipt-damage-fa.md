وضعیت: فقط برنامه‌ریزی — ۱۴۰۴/۰۹/۰۶  
شروع کد فقط بعد از تأیید مالک («شروع کن»).  
شاخهٔ کار جدا از `feature/staff-pay-report`؛ UI سلسله‌مراتب روی `feature/case-process-hierarchy` / PR #56 پایه می‌شود.

## درخواست‌ها (به ترتیب مالک)

1. قسمت مستندات: مثل قبل مشخص باشد فیلم می‌زند یا عکس (دکمه‌های جدا).
2. کارت‌های سلسله‌مراتب (نمای کلی) خیلی بلندند → هر قسمت کشویی باز/بسته شود.
3. بخش تاریخچه هم کشویی شود.
4. در بررسی فنی، هر گروه چک‌لیست (بدنه، برق، موتور، …) هم کشویی شود — فضا زیاد می‌گیرد.
5. لینک مشتری (`/t/...`): بعد از انتخاب عکس رسید، پیش‌نمایش + تأیید / لغو؛ آپلود فقط با تأیید.
6. وقتی مشتری رسید فرستاده: در لیست پرونده‌ها مشخص شود (مثلاً «دارای رسید»)؛ یا روی تب صورتحساب قرمز/نشان‌دار شود.
7. تأیید رسید در فروشگاه: پیش‌فرض مبلغ = ماندهٔ فاکتور؛ اگر بیشتر زد قبل از ذخیره جلویش گرفته شود (نه خطای انگلیسی سرور).
8. باگ مهم: جبران خسارت روی کالا در فاکتور مشتری به‌عنوان «تخفیف» دیده می‌شود — باید «جبران خسارت» باشد، نه تخفیف.

هم‌پوشانی: ۲ و ۴ هر دو «تاشو برای کوتاه کردن صفحه»اند؛ در یک فاز UI.

## ۱) مستندات — دکمهٔ جدا عکس / فیلم

**می‌خواهد:** مشخص باشد کاربر عکس می‌زند یا فیلم.

**امروز:** یک دکمه «عکس یا فیلم» + یک `input` با `accept="image/*,video/*"` (`web/src/photos.tsx`).

**پیشنهاد:**
- دو دکمه کنار هم: «افزودن عکس» و «افزودن فیلم».
- دو `input` جدا (`image/*` با `capture` برای عکس؛ `video/*` برای فیلم).
- در حالت `bare` داخل کارت مستندات همان دو دکمه؛ بج تعداد می‌تواند «N عکس · M فیلم» شود اگر ساده باشد، وگرنه همان «N تصویر» بماند و روی thumb برچسب فیلم بماند.

**داده / API:** بدون تغییر.

**لبه:** ویدیو تا ۲۰۰MB مثل امروز؛ فشرده‌سازی فقط عکس.

**تست:** UI — دو دکمه؛ آپلود عکس و فیلم جدا (دستی روی گوشی).

## ۲ و ۳ و ۴) کشویی: پله‌ها، تاریخچه، گروه‌های چک‌لیست

**می‌خواهد:** صفحه کوتاه‌تر؛ هر بلوک باز/بسته.

**امروز:**
- پله‌های `ProcessStep` (PR #56) همیشه بازند.
- تاریخچه تب کامل باز است.
- گروه‌های چک‌لیست فقط عنوان `<h4>` + chipها؛ تاشو نیستند (کل چک‌لیست قبلاً یک `<details>` بود).

**پیشنهاد:**
- هر `ProcessStep`: `<details>` با همان هدر (آیکون + عنوان + بج)؛ پیش‌فرض: پلهٔ `current` باز، بقیه بسته؛ پلهٔ «درخواست مشتری» اگر `done` باشد بسته.
- تب تاریخچه: کارت رویدادها `<details open>` با خلاصه «N رویداد»؛ یا فقط N تای اول + «نمایش همه» — توصیه: کل کارت تاریخچه تاشو با `open` پیش‌فرض وقتی تب تاریخچه انتخاب شده.
- گروه‌های چک‌لیست داخل عیب‌یابی: هر گروه یک `<details class="case-check-group">`؛ اگر همه تیک خورده بسته، وگرنه باز.
- بخش SMS داخل تاریخچه همان Collapsible فعلی بماند.

**داده / API:** بدون تغییر.

**تست:** دستی — باز/بسته؛ پلهٔ جاری باز؛ گروه ناقص باز.

## ۵) لینک مشتری — پیش‌نمایش رسید قبل از ارسال

**می‌خواهد:** انتخاب عکس → نشان بدهد → تأیید (آپلود) یا لغو.

**امروز:** `PaySheet` در `track.tsx` بلافاصله بعد از انتخاب فایل `POST .../receipts` می‌زند.

**پیشنهاد:**
- بعد از `change` فایل: پیش‌نمایش محلی (`URL.createObjectURL`)، دکمه‌های «تأیید و ارسال» / «لغو».
- آپلود فقط با تأیید؛ لغو فایل را پاک می‌کند و پیش‌نمایش را می‌بندد.
- هنوز مشتری مبلغ نمی‌زند (قانون فعلی).

**داده / API:** بدون تغییر endpoint.

**لبه / سوءاستفاده:** همان محدودیت نوع فایل و حجم؛ revoke کردن object URL بعد از بستن.

**تست:** دستی روی `/t/...`؛ واحد اختیاری اگر منطق جدا شود.

## ۶) نشان «مشتری رسید فرستاده»

**می‌خواهد:** در لیست پرونده‌ها یا روی صورتحساب مشخص شود.

**امروز:** فقط داخل `CustomerReceipts` بج «N در انتظار»؛ لیست case فیلد pending ندارد.

**پیشنهاد (هر دو سطح سبک):**
- API لیست پرونده‌ها: فیلد `pendingReceipts: number` (یا `hasPendingReceipt: bool`) از شمارش رسیدهای `pending` همان tenant/case.
- UI لیست / کارت پرونده: chip نارنجی «رسید مشتری» وقتی `pendingReceipts > 0`.
- تب صورتحساب روی صفحهٔ پرونده: اگر pending > 0، ظاهر هشدار (مثلاً نقطه قرمز روی تب یا کلاس `warn` روی برچسب تب) — بدون قرمز کردن کل UI بی‌دلیل.

**داده:** جدول رسید موجود؛ فقط aggregate در list DTO.

**API:** گسترش پاسخ `GET /api/v1/cases` (و در صورت نیاز detail برای تب).

**تست:** happy path لیست با pending؛ tenant دیگر ۰/۴۰۴؛ بدون permission مثل امروز.

**مجوز:** همان `canRecordPayments` / دید مالی فعلی برای نشان داخل پرونده؛ روی لیست اگر پول نمی‌بیند chip نشان داده نشود یا فقط «رسید» بدون مبلغ.

## ۷) مبلغ تأیید رسید فروشگاه

**می‌خواهد:** پیش‌فرض = عدد فاکتور (مانده)؛ بیشتر از مانده قبل از ذخیره بلاک با پیام فارسی؛ نه خطای انگلیسی validation.

**امروز:**
- پیش‌فرض `claimedRials` (اغلب خالی).
- سرور: `over_balance` با پیام فارسی؛ UI گاهی ProblemDetails عمومی نشان می‌دهد («One or more validation errors occurred»).

**پیشنهاد:**
- پیش‌فرض فیلد = `balanceRials` ماندهٔ قابل پرداخت (همان منطق PaymentSheet فروشگاه).
- قبل از submit: اگر مبلغ > مانده → پیام کنار فیلد: «مبلغ از ماندهٔ فاکتور بیشتر است» و ارسال نشود.
- نمایش خطای سرور: اگر `code === over_balance` همان پیام فارسی؛ هرگز متن انگلیسی خام به کاربر.

**تفسیر مالک:** اجازهٔ پرداخت بیش از فاکتور نمی‌خواهد؛ فقط UX پیش‌فرض + جلوگیریٔ زودهنگام.

**داده / API:** بدون شل کردن قانون سرور.

**تست:** UI؛ در صورت وجود تست API همان `over_balance` سبز بماند.

## ۸) باگ — جبران خسارت ≠ تخفیف (فاکتور مشتری)

**می‌خواهد:** وقتی خسارت به کالا وصل است، در فاکتور مشتری «جبران خسارت» بیاید نه «تخفیف»؛ مبلغ جبران مشخص باشد.

**امروز:**
- مدل داخلی جبران را روی `DiscountRials` کالا می‌نویسد (`DamageCompensation`).
- `track.tsx`: روی ردیف و جمع برچسب «تخفیف» / «جمع قبل از تخفیف».
- فروشگاه تا حدی «جبران خسارت» دارد؛ track مشتری گمراه‌کننده است.

**پیشنهاد:**
- Track API (یا DTO ردیف): برای هر آیتم فلگ/منبع تخفیف: `discountKind: "damage" | "manual" | null` یا `customerDamageId`.
- UI مشتری:
  - ردیف با جبران: «جبران خسارت −…» نه «تخفیف».
  - جمع‌ها: اگر همهٔ کسر از جبران است → «جبران خسارت»؛ اگر مخلوط تخفیف دستی + جبران → دو خط جدا؛ اگر فقط تخفیف دستی → «تخفیف».
- فروشگاه: totals اگر فقط جبران است همان واژه؛ مخلوط دو خط.

**داده:** ترجیحاً بدون migration اگر `customerDamageId` روی `CaseItem` از قبل هست و به track DTO اضافه شود؛ وگرنه فیلد کوچک در پاسخ track.

**تست:**
- happy: کالا با جبران → track برچسب جبران؛ مبلغ درست.
- تخفیف دستی بدون خسارت → همچنان «تخفیف».
- tenant دیگر ۴۰۴ روی track کد غلط.

## فازها (کوچک‌ترین مفید اول)

| فاز | محتوا | اندازه |
