## ۲. قرارداد پیشنهادی سرور (برای تأیید مالک — هنوز اجرا نشده)

### ۲.۱ کلیدهای پایدار نوع درخواست

| Key (API/DB) | برچسب فارسی | RequiresChecklist | جزئیات زیرمجموعه |
|---|---|---|---|
| `wrenching` | آچارکشی | بله | ندارد (اختیاری: شرح مشتری) |
| `engine_repair` | تعمیر موتور | بله | ندارد (اختیاری: شرح مشتری) |
| `tech_inspection` | بازدید فنی | بله | ندارد (اختیاری: شرح مشتری) |
| `other` | سایر درخواست‌ها | خیر | بله — از فهرست ایراد/خدمت فعلی (مثلاً تعویض چرخ، صفحه‌کلاچ، تعویض روغن) |

- چند نوع در یک پرونده مجاز است (مثلاً `wrenching` + `other`).  
- حداقل یک نوع درخواست برای ایجاد پرونده لازم است (پیشنهاد).  
- برچسب فارسی فقط برای نمایش؛ اعتبارسنجی با **Key** است.

### ۲.۲ مدل دادهٔ پیشنهادی

- فیلد جدید روی `Case`: `RequestTypes` به‌صورت `string[]` کلیدهای بالا (یا جدول رابط در صورت نیاز بعدی به متادیتا).  
- آرایه‌های فعلی `ReportedProblems` و `RequestedServices` **حفظ** می‌شوند برای جزئیات زیر `other` (و در صورت تمایل، یادداشت کمکی).  
- اگر `other` در `RequestTypes` نباشد، ثبت ایراد/خدمت **مجاز** است (پاسخ A مالک ۱۴۰۵/۰۹/۰۴). برای create، وجود حداقل یک نوع کافی است؛ خالی بودن ایراد/خدمت نباید ثبت را مسدود کند (کد امروز سخت‌گیرانه‌تر است و در برش فلو باید هم‌خوان شود).  
- جدول/کاتالوگ سروری `RequestTypeDefinition` (seed سیستم + امکان توسعهٔ بعدی tenant):  
  `Key`, `TitleFa`, `RequiresChecklist`, `AllowsDetailLists`, `SortOrder`, `IsActive`.  
- نگاشت چک‌لیست: `RequestTypeChecklistBinding`  
  - `RequestTypeKey`  
  - `MotorType` (`geared` | `automatic` | null = هر دو)  
  - ارجاع به همان `ChecklistTemplateItem`های فعلی (فیلتر با `MotorType`) **یا** شناسهٔ مجموعهٔ قالب در آینده  
  - پیش‌فرض seed: سه نوع نیازمند چک‌لیست → همان قالب موتورسیکلت موجود به تفکیک `MotorType` وسیله  
- `Case.MotorType` وقتی حداقل یک نوعِ `RequiresChecklist` انتخاب شده **اجباری** است (برای انتخاب قالب دنده‌ای/اتومات).  
- اگر چند نوع نیازمند چک‌لیست هم‌زمان انتخاب شوند: **یک** مجموعهٔ ردیف قالب (بدون تکرار) برای همان `MotorType` اعمال می‌شود.

### ۲.۳ API پیشنهادی

1. `GET /api/v1/request-types`  
   خروجی: کلید، عنوان، `requiresChecklist`, `allowsDetailLists`, و در صورت نیاز خلاصهٔ binding.  
2. `POST /api/v1/cases` (گسترش):  
   - `requestTypes: string[]` (الزامی)  
   - `reportedProblems` / `requestedServices` طبق قاعدهٔ `other`  
   - `motorType` + `checklist` وقتی سرور تشخیص دهد حداقل یک نوع نیازمند چک‌لیست است  
3. اعتبارسنجی سرور (نه UI):  
   - کلید نامعتبر → 400  
   - نوع نیازمند چک‌لیست بدون `motorType` یا بدون تیک ردیف‌های `IsRequired` قالب → 400 (همان پیام‌های فعلی چک‌لیست)  
   - فقط `other` → چک‌لیست پذیرفته/ذخیره نشود (orphan ممنوع)  
4. پاسخ جزئیات پرونده: `requestTypes` + تعاریف برای نمایش برچسب؛ چک‌لیست پرونده مثل امروز روی `CaseChecklistItem`.

### ۲.۴ رفتار UI وابسته (پس از تأیید قرارداد — هنوز کد نزنیم)

- مرحلهٔ ۲: چهار گزینهٔ چندانتخابی سطح بالا.  
- با انتخاب هر نوعِ نیازمند چک‌لیست: بخش چک‌لیست (پس از انتخاب نوع موتور) ظاهر شود؛ منبع ردیف‌ها از API قالب، نه لیست سخت‌کد کلاینت.  
- با فقط `other`: بدون چک‌لیست؛ چیپ‌های ایراد/خدمت.  
- فهرست/پرونده: برچسب انواع درخواست (+ جزئیات `other` در صورت وجود).

### ۲.۵ مهاجرت و سازگاری

- پرونده‌های قدیمی بدون `RequestTypes`: در خواندن می‌توان خالی یا استنتاج نمایشی از `RequestedServices` نشان داد؛ **بدون بازنویسی خاموش تاریخچه** تا تصمیم مهاجرت (سؤال B).  
- قالب‌های فعلی `ChecklistTemplateItem` بر اساس `MotorType` حفظ می‌شوند؛ binding فقط «کی لازم است» را عوض می‌کند، نه لزوماً محتوای ردیف‌ها در نسخهٔ اول.

### ۲.۶ خارج از این قرارداد (عمداً)

- ساعت کارکرد، صف پیامک PR #21، صفحهٔ کاتالوگ، نظرسنجی یک‌صفحه‌ای.  
- چند قالب کاملاً متفاوت per-request در نسخهٔ اول (مگر مالک خلاف بخواهد — سؤال C).

## ۳. هم‌راستایی با Make / Figma

**دسترسی MCP:** ابزارهای Figma Design روی URL از نوع `figma.com/make/...` پشتیبانی نمی‌شوند؛ فریم Design جدا برای Make در دسترس این عامل نبود.

**بررسی محلی خروجی Make** (`Redesign Art Service Flows.zip`):

| صفحهٔ Make | مشاهده | هم‌خوانی با تصمیم محصول |
|---|---|---|
| `Intake.tsx` | Make: استپر ۴تایی با مشتری/وسیله جدا | **استپر بیرونی هدف Arte = ۳تایی** (مشتری+وسیله با هم؛ سند ۲۸). کارت→جزئیات از Make الهام؛ ظاهر Arte |
| `CaseDetail.tsx` | سربرگ وسیله/مشتری/وضعیت، اقدام بعدی برجسته، تب نمای‌کلی/صورتحساب/تاریخچه، شیت اقدامات، تگ درخواست‌ها | نزدیک به مشخصات پرونده؛ مرجع خوب برای جزئیات بصری پس از قفل مشخصات |
| `Cases.tsx` | فیلتر، جست‌وجو، کارت با پیشرفت و مانده | مرجع فهرست؛ باید با فیلترهای فعلی محصول ادغام شود نه جایگزین کور |
| `Minimal iPhone Design` | عمدتاً پیگیری مشتری + نظرسنجی | خارج از دامنهٔ پذیرش کارگاه |

**پیشنهاد ثبت (به‌روز):** مرجع فلو پذیرش = سند ۲۸ (۳ استپر بیرونی + کارت→جزئیات)؛ ظاهر = دیزاین‌سیستم Arte. مرجع پرونده/فهرست = Make CaseDetail/Cases با توکن Arte.

## ۴. موارد باز باقیمانده (مالک باید پاسخ دهد)

> **E / S / A / B / I به‌روز ۱۴۰۵/۰۹/۰۴:** استپر ۳تایی + کارت→جزئیات قطعی؛ نگاشت = **تعویق D**؛ A=مجاز بدون الزام سایر و نوع کافی برای create؛ B=سایر برای بی‌نوع (قبلی)؛ برش اول = فلو بدون نگاشت.

**A.** ✅ بسته — مجاز؛ نوع کافی برای create.  
**B.** ✅ بسته — Effective/نمایش «سایر».  
**C.** در نسخهٔ اول، آیا هر سه نوع نیازمند چک‌لیست **همان** قالب geared/automatic فعلی را سهم می‌برند، یا قالب جدا؟  
**D.** ردیف‌های `IsRequired`: همچنان مانع **شروع کار** — تأیید نهایی واژه‌ها؟  
**F.** قیمت فروش خالی تا تحویل — قاعده برای کالای نصب‌نشده / مشتری / لغو؟  
**G.** گیرندهٔ پیش‌فرض پیامک داخلی و مجوز؟  
**H.** صف اقدام: تقویت خانه یا ویجت جدا؟  
**I.** ✅ برش اول = فلو بدون نگاشت (D)؛ با «شروع کن: فلو پذیرش سند ۲۸ بدون نگاشت خدمات».  
**S.** ✅ S2=D؛ جدول نگاشت تأیید نشد (بایگانی در سند ۲۸).
