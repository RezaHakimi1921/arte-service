## جمع درخواست‌ها (به همان ترتیب شما)

1. منطق شارژ پیامک مال Arte باشد؛ SmartX فقط لولهٔ `direct-send` است و کیف شعبه را کم نمی‌کند.
2. مخزن مرکزی Arte بعد از خرید از اسمارت (فعلاً ثبت دستی / `central-topup`).
3. شارژ هر شعبه داخل Arte + شارژ دستی ادمین.
4. ارسال غیر OTP: شمارش پارت در Arte، کسر از کیف شعبه (نرخ فروش ۲۱۹ تومان)، اثر تقریبی خرید (×۱۰۰) روی مخزن مرکزی.
5. OTP ورود: فعلاً Faraz (نه sms.ir)؛ از شارژ شعبه کم نشود.
6. قبل از ارسال: اگر کیف شعبه کافی نبود → رد با خطای واضح؛ به کسر اسمارت تکیه نکنیم.
7. همهٔ پیام‌ها غیر از OTP روی SmartX.
8. همین الان: مخزن اصلی ۱ میلیون تومان؛ شعبهٔ «مکانیک موتور» ۱۰۰ هزار تومان.
9. لایسنس: ثبت‌نام پیش‌فرض تا ۱۵ پروندهٔ رایگان (همهٔ خدمات شامل نظرسنجی).
10. بعد از ۱۵ پرونده: قفل پذیرش جدید + هدایت به خرید لایسنس؛ کار روی پرونده‌های موجود باز بماند.
11. لایسنس هدیه (رایگان توسط ادمین پلتفرم) بماند.
12. در UI نشان بدهد چند پروندهٔ رایگان مانده.
13. تغییر متن قالب پیامک فقط برای ادمین پلتفرم (شما)؛ شعبه فقط درخواست بدهد / اطلاع بدهد.
14. کارها با PR و build از مسیر git به شما برسد تا بررسی کنید.

موارد ۱–۷ و ۸ با هم هم‌پوشانی دارند: ۱–۷ قانون محصول؛ ۸ عملیات فوری.

## ۱ تا ۸ — پیامک و کیف

### الان چه هست
- `SmsWalletService`: مخزن مرکزی + کیف هر شعبه به **پارت**؛ خرید پیش‌فرض ۱۰۰ تومان، فروش ۲۱۹ تومان؛ کسر شرطی؛ refund اگر اسمارت نپذیرد.
- `SmartXSmsProvider` قبل از ارسال از کیف کم می‌کند؛ OTP از مسیر SmartX نمی‌رود (`RoutingSmsProvider` + Faraz).
- پنل ادمین «پیامک و شارژ» و دستور `sms-wallet` روی سرور.
- تست واقعی direct-send به گوشی شما موفق بود (`204`).

### عملیات همین جلسه (انجام‌شده)
| کار | نتیجه |
|---|---|
| مخزن مرکزی +۱٬۰۰۰٬۰۰۰ تومان | با نرخ خرید ۱۰۰ → **۱۰٬۰۰۰ پارت** (`central-topup 10000`) |
| «مکانیک موتور» +۱۰۰٬۰۰۰ تومان | با نرخ فروش ۲۱۹ → **۴۵۶ پارت** |
| همه غیر OTP → SmartX | `SMARTX_ALL=true` روی سرور؛ OTP = Faraz |

### پیشنهاد باقی‌مانده (کد / UX)
- خطای `insufficient_credit` را در UI پرونده فارسی و واضح نشان بدهیم («شارژ پیامک شعبه تمام شده…»).
- در ادمین: ثبت فاکتور پس‌کرایه (مبلغ تومان + یادداشت فاکتور) کنار top-up.
- OTP را **تا اطلاع بعدی** روی Faraz نگه می‌داریم؛ وقتی بگویید، جداگانه به SmartX منتقل می‌شود (و همچنان از کیف شعبه کم نمی‌شود).

### داده / API
جدول‌های فعلی کافی‌اند (`SmsSettings`, `SmsWallets`, `SmsLedger`). نیاز فوری به migration نیست مگر فیلد «شماره فاکتور اسمارت».

### تست
- شارژ مرکزی و شعبه، کسر با ارسال، رد وقتی موجودی کم است، OTP بدون کسر شعبه، refund وقتی اسمارت رد کند.

## ۹ تا ۱۲ — لایسنس بر پایهٔ ۱۵ پرونده

### الان چه هست
- Trial زمانی: **۱۴ روز** از ثبت‌نام (`LicensePolicy.TrialDays`).
- `Gift` و `Paid` از قبل هست.
- قفل فعلی: فقط POST پذیرش/مشتری/همکار وقتی لایسنس زمانی تمام شده (`402 license_expired`)؛ پرونده‌های باز قابل ادامه‌اند.

### پیشنهاد
- Trial پیش‌فرض = **۱۵ پرونده** (نه روز). شمارش: پرونده‌های ساخته‌شدهٔ شعبه با `DeletedAt IS NULL`.
- تا وقتی لایسنس `paid` یا `gift` فعال زمانی دارد → محدودیت ۱۵ اعمال نشود.
- وقتی فقط trial پرونده‌ای است و تعداد ≥ ۱۵ → همان قفل رشد (`402`) با کد جدا مثل `trial_cases_exhausted` و متن فارسی هدایت به خرید.
- `GET /api/v1/license` برگرداند: `freeCasesLeft` / `freeCasesUsed` / `freeCasesLimit`.
- UI: در خانه یا کنار «پذیرش جدید» بماند «X پروندهٔ رایگان مانده»؛ صفحهٔ قفل با دکمهٔ تماس/خرید.
- هدیه: همان `kind=gift` ادمین؛ می‌تواند ماه بدهد یا (اختیاری فاز بعد) سقف پروندهٔ اضافه.

### داده
- یا فیلد روی Tenant/`License`: `TrialCaseLimit = 15`؛ یا فقط ثابت در `LicensePolicy`.
- توصیه: ثابت ۱۵ در policy + امکان override ادمین بعداً.

### لبه و سوءاستفاده
- soft-delete پرونده نباید سهمیه را برگرداند (پیشنهاد: شمارش همهٔ ساخته‌شده‌ها، حتی حذف‌شده؛ یا فقط غیرحذف — **سؤال باز**).
- شعبهٔ چندبرندی: سقف per tenant (شعبه)، نه کل برند.

### تست
- ثبت‌نام → ۱۴ پرونده OK، ۱۵م OK، ۱۶م 402؛ بعد gift → دوباره پذیرش؛ tenant دیگر جدا.

## ۱۳ — قالب پیامک فقط ادمین پلتفرم

### الان چه هست
- شعبه متن را می‌بیند (پیش‌نمایش در تنظیمات مشتری).
- ادمین پلتفرم draft / approve / reset در `smsAdmin`.

### پیشنهاد
- شعبه **نتواند** متن قالب را ذخیره کند؛ فقط پیش‌نمایش سیستم + دکمهٔ «درخواست تغییر متن» (متن پیشنهادی + توضیح).
- اعلان برای ادمین پلتفرم (فعلاً: ردیف در پنل ادمین / بعداً پیامک به شما).
- فقط شما approve می‌کنید؛ تا approve، متن سیستم ارسال می‌شود.

### تست
- عضو شعبه PUT قالب → 403؛ ادمین approve → ارسال با متن جدید.

## ۱۴ — مسیر PR و build

### پیشنهاد فرآیند
1. کار روی branch با نام واضح (`feature/…` / `fix/…`).
2. `gh pr create` → CI (build + test) روی PR.
3. شما در GitHub بررسی و Approve.
4. Merge به `main` فقط بعد از تأیید شما.
5. Deploy دستی (`workflow_dispatch`) بعد از merge — مثل امروز.
6. قبل از دست زدن به `main`: snapshot روی `Juck` (قانون فعلی).

از این به بعد مستقیم روی `main` push نمی‌کنیم مگر خودتان بگویید.

## سؤال‌های باز (با پیشنهاد من)

1. **شمارش ۱۵ پرونده:** پروندهٔ soft-delete شمرده شود؟  
   **پیشنهاد:** بله شمرده شود تا با حذف عمدی سقف دور زده نشود.
2. **بعد از خرید لایسنس زمانی، شمارش trial رها شود؟**  
   **پیشنهاد:** بله؛ با `paid`/`gift` فعال، سقف ۱۵ اعمال نشود.
3. **درخواست تغییر قالب:** فقط تیکت داخل ادمین کافی است یا پیامک به موبایل شما هم؟  
   **پیشنهاد:** فاز اول فقط لیست در ادمین؛ پیامک بعداً.
4. **نرخ ۱۰۰/۲۱۹ برای شارژ امروز درست بود؟** (۱M → ۱۰٬۰۰۰ پارت؛ ۱۰۰هزار → ۴۵۶ پارت)  
   **پیشنهاد:** اگر مبلغ فاکتور اسمارت فرق دارد بگویید تا central را sync کنیم.
5. **PR برای همین برنامه:** بعد از «شروع کن» هر فاز یک PR جدا؟  
   **پیشنهاد:** بله — B و C جدا؛ A اگر فقط UX کوچک است با B یاalone.
