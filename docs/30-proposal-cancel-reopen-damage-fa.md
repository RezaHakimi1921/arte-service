**وضعیت:** فقط پیشنهاد محصول و تست — **تصمیم مالک قفل نشده**؛ هیچ کد / API / migration در این برش نیست.  
**تاریخ:** ۱۴۰۵/۰۹/۰۴  
**مرجع:** [۲۴](24-implementation-roadmap-fa.md) گام دو بند ۳؛ [۲۷](27-plan-case-page-figma-fa.md) بخش «بعداً»؛ [۲۵](25-owner-decisions-intake-process-fa.md)؛ [مشخصات فلو](arte-intake-cases-flow-spec-fa.md)؛ مدل دامنه ۰۳؛ کد فعلی `motorcycle_repair.json` + `CaseEndpoints.TransitionAsync`.

## ۱. خواستهٔ این برش (به زبان مالک)

1. **لغو پرونده** ثبت‌شده با دلیل روشن و قابل‌مشاهده در تاریخچه.  
2. **بازگشایی پرونده** (امروز: برچسب «بازگشایی در ضمانت») با دلیل، اثر بر گردش‌کار و تاریخچه.  
3. **ثبت خسارت مستقل** روی پرونده — جدا از وضعیت/شرح بدنهٔ پذیرش.

## ۲. آنچه امروز هست (شاهد کد / تست)

### ۲.۱ لغو

| مورد | امروز |
|---|---|
| از کجا | فقط از `received`، `diagnosing`، `awaiting_approval` → `cancelled` |
| برچسب | «انصراف» یا «مشتری رد کرد» |
| دلیل | اجباری (`RequiresReason`)، متن آزاد تا ۵۰۰ حرف؛ **فهرست دلیل ثابت نیست** |
| مجوز | `cases.create` (+ دیدن پرونده) |
| تاریخچه | `case.stage_changed` + `case.cancelled` با دلیل |
| چک‌لیست ناقص | مانع لغو نیست |
| از مراحل دیگر | از `repairing` / `awaiting_parts` / `review` / `ready` مسیر لغو در قالب نیست |
| پیش‌نویس ثبت‌نشده | لغو پرونده نیست؛ بستن فرم پذیرش جداست |

تست: `Cancel_needs_a_reason` در `CaseTests`.

### ۲.۲ بازگشایی

| مورد | امروز |
|---|---|
| از کجا | فقط `delivered` → `received`، برچسب «بازگشایی در ضمانت» |
| دلیل | اجباری، متن آزاد تا ۵۰۰ حرف |
| مجوز | `cases.create` |
| تاریخچه | `case.stage_changed` + `case.reopened`؛ `ClosedAt` پاک می‌شود؛ `CustodyStatus` → در مغازه |
| نظرسنجی | دعوت ارسال‌نشده لغو می‌شود (`CancelUnsentAsync`) |
| ضمانت در کد | فیلد `WarrantyUntil` هنگام تحویل ست می‌شود، ولی **گذار بازگشایی تاریخ ضمانت را چک نمی‌کند** — هر پروندهٔ تحویل‌شده با مجوز قابل بازگشایی است |
| از `cancelled` | مسیری در قالب نیست |
| خارج از ضمانت | برچسب می‌گوید «در ضمانت»، ولی سخت‌گیری سرور نیست |

تست: `Delivered_case_can_be_reopened_under_warranty_with_a_reason` (دلیل و رویداد؛ نه بازهٔ ضمانت).

### ۲.۳ وضعیت / شرح بدنه (الان — نه خسارت مستقل)

| مورد | امروز |
|---|---|
| فیلدها | `BodyStatus`: `ok` \| `damaged`؛ `BodyNotes` (وقتی آسیب) |
| کجا | پذیرش؛ قابل PATCH روی پرونده |
| ماهیت | **یک خلاصهٔ تک‌مقداری** روی خود پرونده |
| سابقه | تغییر در رویدادهای ویرایش؛ فهرست جدا از «خسارت‌ها» نیست |
| عکس | پیوست عمومی پرونده؛ به ردیف خسارت وصل نیست |

### ۲.۴ خسارت مستقل

**وجود ندارد.** سند ۲۷ آن را خارج از دامنهٔ فاز ۱–۳ صفحهٔ پرونده گذاشته؛ سند ۲۴ تا تصمیم مالک پیاده‌سازی را متوقف کرده است.

## ۳. تفاوت پیشنهادی: بدنهٔ پذیرش در برابر خسارت مستقل

| | وضعیت/شرح بدنه | خسارت مستقل (پیشنهاد) |
|---|---|---|
| نقش | چک سریع هنگام پذیرش: سالم / آسیب دیده + یک شرح | سابقهٔ قابل‌افزودن روی پرونده برای بازبینی بعدی |
| تعداد | یک وضعیت جاری | چند ردیف در طول عمر پرونده |
| زمان | عمدتاً پذیرش (ویرایش بعدی ممکن است) | پذیرش و/یا حین کار — **تصمیم باز مالک** |
| کی؟ | هر کسی که پرونده را ویرایش می‌کند (قواعد فعلی edit) | پیشنهاد: حداقل همان سطح دیدن + کار/ایجاد — **تصمیم باز** |
| عکس | عکس پروندهٔ عمومی | پیشنهاد: پیوست اختیاری به همان ردیف |
| جایگزین هم؟ | خیر — بدنه می‌ماند | خسارت، بدنه را حذف یا جایگزین نمی‌کند |

**پیشنهاد محصول (غیرقطعی):** بدنه همان چک پذیرش بماند؛ خسارت مستقل برای «چه آسیبی، کی دیده شد، کی ثبت کرد، آیا عکس دارد» اضافه شود. دو نوع مفهومی در UI از هم جدا نوشته شوند: مثلاً «آسیب از قبل روی وسیله» و «کشف / رخداد حین کار» — برچسب نهایی با مالک.

## ۴. پیشنهاد محصول — لغو

### ۴.۱ رفتار حفظ‌شده (پایه)

- دلیل اجباری؛ در timeline خوانا (`case.cancelled` + دلیل در `stage_changed`).  
- مجوز `cases.create` (طبق قالب فعلی).  
- متمایز از بستن پیش‌نویس ثبت‌نشده و از soft-delete پرونده.

### ۴.۲ گزینه‌های نیازمند تصمیم (قفل نشده)

| # | موضوع | گزینه‌ها | توصیهٔ Cursor (فقط پیشنهاد) |
|---|---|---|---|
| L1 | دامنهٔ مراحل لغو | الف) همان سه مرحلهٔ فعلی ب) گسترش به `repairing` / `awaiting_parts` / `review` / `ready` | فعلاً الف؛ گسترش فقط اگر کارگاه واقعاً از وسط کار انصراف می‌دهد |
| L2 | فهرست دلیل | الف) متن آزاد ب) چند گزینهٔ ثابت + «سایر» با شرح | ب برای گزارش؛ گزینه‌ها را مالک بنویسد |
| L3 | پول / قطعه بعد از لغو | الف) بدون تغییر ب) هشدار مانده/قطعه ج) مسدود تا تسویه | الف + هشدار در UI؛ مسدود نکن مگر مالک بگوید |
| L4 | پیامک مشتری هنگام لغو | الف) نه ب) بله با قالب | فعلاً الف (صف پیامک هنوز باز است) |

### ۴.۳ نقش‌ها (امروز)

| نقش پیش‌فرض | لغو؟ |
|---|---|
| مالک (`cases.create`) | بله |
| استاد / ناظر (معمولاً `cases.create`) | بله |
| تعمیرکار (فقط work + intake) | خیر، مگر مجوز create داده شود |
| کارآموز | خیر |

## ۵. پیشنهاد محصول — بازگشایی

### ۵.۱ رفتار حفظ‌شده (پایه)

- از تحویل‌شده به پذیرش با دلیل؛ رویداد `case.reopened`؛ پاک‌شدن `ClosedAt`؛ برگشت نگهداشت به مغازه؛ لغو نظرسنجی ارسال‌نشده.

### ۵.۲ شکاف مهم

برچسب UI/قالب «در ضمانت» است، ولی سرور `WarrantyUntil` را برای اجازهٔ گذار چک نمی‌کند. این باید یا در محصول هم‌خوان شود یا برچسب عوض شود — **بدون تصمیم مالک یکی را قفل نمی‌کنیم.**

### ۵.۳ گزینه‌های نیازمند تصمیم

| # | موضوع | گزینه‌ها | توصیهٔ Cursor |
|---|---|---|---|
| R1 | سخت‌گیری ضمانت | الف) فقط وقتی `now ≤ WarrantyUntil` ب) همیشه با دلیل (رفتار کد امروز) ج) دو دکمه: در ضمانت / خارج از ضمانت | الف برای هم‌خوانی با برچسب؛ ج اگر کارگاه خارج از ضمانت هم نیاز دارد |
| R2 | وقتی ضمانت خالی است (`WarrantyUntil` تهی) | الف) بازگشایی ممنوع ب) مجاز با هشدار ج) مثل خارج از ضمانت | ب تا کارگاه گیر نکند |
| R3 | بازگشایی از `cancelled` | الف) نه (امروز) ب) بله با دلیل و مجوز بالاتر | فعلاً الف |
| R4 | پروندهٔ جدید برگشتی در برابر بازگشایی همان پرونده | هر دو امروز هست (`ParentCaseId` / comeback در برابر reopen) | هر دو بمانند؛ در UI فرق «همین پرونده» و «پروندهٔ جدید برگشتی» روشن شود |
| R5 | اثر مالی بازگشایی | اجرت/قطعهٔ جدید صفر پیش‌فرض در ضمانت؟ | طبق دامنه ۰۳ برای برگشتی؛ برای reopen همان پرونده در برش کد جدا روشن شود |

## ۶. پیشنهاد محصول — خسارت مستقل

### ۶.۱ مدل مفهومی (پیشنهاد؛ schema قفل نیست)

هر ردیف تقریباً:

- شرح (اجباری، سقف طول مثل سایر فیلدهای متنی پروژه)
- گونه: `pre_existing` \| `found_during_work` \| `occurred_during_work` (نام‌ها پیشنهادی)
- زمان ثبت (UTC سرور)
- ثبت‌کننده (عضویت)
- پیوست عکس اختیاری (۰…N؛ فشرده‌سازی مثل عکس پرونده)
- soft-delete + restore (قاعدهٔ پروژه)
- `ITenantOwned`

`BodyStatus` / `BodyNotes` **حذف یا ادغام اجباری نمی‌شوند.**

### ۶.۲ UI (پیشنهاد)

- بخش تاشو در صفحهٔ پرونده: «خسارت‌ها» با افزودن ردیف + لیست زمانی.  
- در پذیرش: اختیاری — یا فقط بدنه، یا «ثبت خسارت» که اولین ردیف را بسازد؛ **تصمیم باز.**  
- مشتری لینک عمومی: پیش‌فرض فقط بدنه/عکس‌های مجاز؛ ردیف‌های خسارت داخلی مگر مالک بگوید دیده شود.

### ۶.۳ گزینه‌های نیازمند تصمیم

| # | موضوع | گزینه‌ها | توصیهٔ Cursor |
|---|---|---|---|
| D1 | زمان مجاز ثبت | فقط پذیرش / پذیرش+حین کار / همیشه تا قبل از تحویل / حتی بعد از تحویل | پذیرش + حین کار تا قبل از تحویل |
| D2 | ویرایش بعد از ثبت | فقط افزودن / ویرایش شرح تا X ساعت / فقط soft-delete | افزودن + soft-delete؛ ویرایش محدود |
| D3 | مجوز | `cases.work` روی پروندهٔ خود / `cases.create` / مجوز تازه | فعلاً `cases.work` برای افزودن روی پروندهٔ قابل‌کار؛ دیدن برای همهٔ `CanSee` |
| D4 | الزام عکس وقتی گونه «رخداد حین کار» | بله / خیر | خیر در MVP؛ توصیه در UI |
| D5 | پیوند به مرحله | ذخیرهٔ `stageKey` لحظهٔ ثبت؟ | بله، برای تاریخچه |
| D6 | گزارش / فیلتر | بعداً | خارج از برش اول |

## ۸. معیارهای پذیرش و تست (پس از «شروع کن»؛ الان اجرا نمی‌شود)

### ۸.۱ لغو

- خوش‌مسیر با دلیل از هر مرحلهٔ مجاز → `cancelled` + رویدادها.  
- بدون دلیل → ۴۰۰.  
- بدون مجوز → ۴۰۳؛ tenant دیگر → ۴۰۴.  
- چک‌لیست ناقص مانع لغو نباشد.  
- UI: دلیل در timeline فارسی؛ دکمهٔ خطر برای انصراف.

### ۸.۲ بازگشایی

- خوش‌مسیر تحویل‌شده با دلیل → `received` + `case.reopened`.  
- بدون دلیل → ۴۰۰؛ بدون مجوز → ۴۰۳.  
- اگر R1=الف: خارج از `WarrantyUntil` → رد با پیام فارسی روشن.  
- نظرسنجی ارسال‌نشده بعد از reopen لغو شود (رگرسیون).  
- از `cancelled` تا تصمیم R3 نباید مسیر باز شود.

### ۸.۳ خسارت مستقل

- افزودن ردیف با شرح؛ لیست روی detail؛ tenant isolation.  
- بدون مجوز → ۴۰۳.  
- soft-delete پنهان از لیست عادی؛ restore در صورت دامنه.  
- بدنهٔ پذیرش بعد از افزودن خسارت دست‌نخورده بماند.  
- عکس متصل فقط از API احراز هویت‌شده (مثل پیوست فعلی).

### ۸.۴ دستی / QA موبایل

- ۳۷۵px، هر دو تم؛ شیت دلیل؛ بخش خسارت تاشو؛ نقش تعمیرکار در برابر مالک.

## ۱۱. پرسش‌های باز برای مالک (پاسخ لازم قبل از کد)

لطفاً برای هر مورد یکی را انتخاب کنید یا «بعداً» بگویید:

1. **L1** دامنهٔ لغو: فقط سه مرحلهٔ فعلی یا گسترش؟  
2. **L2** دلیل لغو: آزاد یا فهرست + سایر؟ اگر فهرست، متن گزینه‌ها؟  
3. **R1 / R2** آیا بازگشایی باید واقعاً به بازهٔ ضمانت محدود شود؟ اگر `WarrantyUntil` خالی باشد چه؟  
4. **R3** بازگشایی از پروندهٔ لغوشده؟  
5. **D1** خسارت مستقل از کی تا کی قابل ثبت است؟  
6. **D3** چه کسی می‌تواند خسارت ثبت کند؟  
7. آیا در پذیرش علاوه بر بدنه، ساخت اولین ردیف خسارت هم باشد؟  
8. مشتری روی لینک پیگیری خسارت‌های مستقل را ببیند؟

تا پاسخ این‌ها و «شروع کن: …»، کدی زده نمی‌شود و هیچ گزینهٔ بالا به‌عنوان تصمیم قطعی ثبت نمی‌شود.
