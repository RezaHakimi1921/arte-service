**وضعیت:** سؤالات باز ۱–۸ پاسخ داده شد (۱۴۰۵/۰۹/۰۲) — **فاز ۱ در حال پیاده‌سازی**.

## جمع‌بندی یک‌خطی

پذیرش باید چندمرحله و چندبخش شود (مشتری/وسیله → درخواست‌ها → فقط بخش‌های لازم مثل چک‌لیست آچارکشی/تعمیر موتور). پیامک بدون اعتبار باید صف و ارسال مجدد بگیرد. محصولات، کیلومتر/ساعت، برند آزاد، پیش‌فرض انجام‌دهنده، نظرسنجی یک‌صفحه‌ای و گیرندگان پیامک استاد هم در همین بسته اصلاح می‌شوند.

## وضعیت امروز (کوتاه)

| موضوع | امروز |
|--------|--------|
| پذیرش | یک فرم اسکرول؛ مشکلات + خدمات دسته‌بندی؛ چک‌لیست فقط برای موتورسیکلت (دستی/اتومات)، نه per-درخواست |
| پیامک بدون اعتبار | soft-skip؛ صف ارسال بعد از شارژ **نیست** |
| برند/مدل آزاد | فیلدها و Attributes هست؛ باگ «اضافه شد سیو نشد» باید روی CASE واقعی بازتولید شود |
| ساعت کارکرد | فقط `OdometerKm` |
| کاتالوگ | افزودن تکی؛ شیت پایین برای add/edit؛ خرید اجباری نیست |
| انجام‌دهنده | پیش‌فرض عضو فعلی / خالی، نه assignee |
| نظرسنجی مشتری | auto-advance بین سؤال‌ها |
| پیامک استاد | روی انتقال به بازبینی (`staff.work_finished`)، نه دقیقاً «قبل از تحویل»؛ گیرنده = تا ۳ نفر با `CasesCreate` |

## پیشنهاد به تفکیک مورد

### الف) پذیرش چندمرحله و چندبخش — ۱، ۲، ۳، ۴، ۷، ۸، ۹

**پیشنهاد UI:**  
1. مرحلهٔ مشتری + وسیله (با ضربدر پاک‌کردن وسیلهٔ انتخاب‌شده — مورد ۹).  
2. مرحلهٔ درخواست‌ها: چند انتخاب از دسته‌ها (آچارکشی، تعمیر موتور، خدمات/قطعهٔ درخواستی مثل صفحه کلاچ، تعویض چرخ، …).  
3. فقط برای درخواست‌هایی که «نیازمند چک‌لیست» علامت خورده‌اند، سکشن چک‌لیست بیاید.  
4. بقیهٔ فیلدها (عکس، مسئول، …) در همان جریان یا تکمیل بعدی طبق قواعد فعلی.

**داده:** پرچم روی نوع خدمت/قالب (`RequiresChecklist`) یا نگاشت دسته → چک‌لیست؛ چند درخواست روی یک پرونده (لیست مشکل/خدمت موجود گسترش می‌یابد، نه دو سیستم).  
**Figma (مورد ۱):** قبل از کد UI، فریم پذیرش را در Figma مشخص کنید (لینک/node) یا بگویید از `Minimal iPhone Design` کدام فریم.  
**تست:** ثبت چند درخواست؛ فقط آچارکشی → چک‌لیست؛ فقط تعویض چرخ → بدون چک‌لیست؛ ضربدر وسیله.

### ب) پیامک صف بعد از شارژ — ۵، ۶

**پیشنهاد:** وقتی ارسال به خاطر نبود اعتبار رد می‌شود، رکورد pending بماند (نوع پیام، پرونده، گیرنده، پارت). بعد از شارژ موفق شعبه، worker همان صف را بفرستد (با سقف تلاش و CaseEvent/لاگ). OTP ورود وارد این صف نشود.  
**هم‌پوشانی با ۲۰:** لایهٔ اعتماد UX جدا می‌ماند؛ این صف عملیاتی است.  
**تست:** بدون اعتبار → pending؛ شارژ → ارسال؛ tenant دیگر نببیند.

### ج) برند/مدل و ساعت — ۱۰، ۱۱

**۱۰:** بازتولید باگ سیو «سایر»؛ اگر فقط کلاینت است درست شود؛ اگر سرور title/attributes را می‌ریزد تست API. فهرست برند موتور را در `vehicles.ts` غنی‌تر کنید ولی مسیر آزاد همیشه سیو شود.  
**۱۱:** روی وسیله یا پرونده: واحد کارکرد `km` | `hours` + مقدار؛ UI برچسب عوض شود؛ گزارش‌ها هر دو را بفهمند.  
**تست:** سیو CB آزاد؛ پرونده با ساعت نه کیلومتر.

### د) محصولات — ۱۲، ۱۳، ۱۴

**۱۲:** انتخاب چندقلم در یک صفحه → یک ثبت دسته‌ای کاتالوگ (یا چند POST پشت‌هم با یک UI).  
**۱۳:** خرید (cost) اجباری؛ فروش اختیاری (null/۰ تا تحویل)؛ قاعدهٔ «خرید ≤ فروش» فقط وقتی فروش پر است.  
**۱۴:** add/edit کاتالوگ = صفحهٔ کامل (نه فقط BottomSheet)؛ لیست همان CatalogView بهبود یابد.  
**تست:** ۵ قلم یکجا؛ بدون فروش OK؛ فروش کمتر از خرید رد.

### هـ) انجام‌دهنده — ۱۵

پیش‌فرض `PerformedBy` = `Case.AssigneeId` اگر باشد؛ وگرنه انتخاب دستی.  
**تست:** با مسئول پرونده → پیش‌فرض همان؛ بدون مسئول → خالی یا قانون توافقی.

### و) نظرسنجی — ۱۶

مشتری: همهٔ سؤال‌ها یک صفحه (برداشتن auto-advance).  
کارگاه/مدیر: صفحهٔ لیست نظرسنجی‌ها (نه فقط صف رضایت پایین در خانه).  
**تست:** ثبت یک‌باره؛ لیست با فیلتر تاریخ.

### ز) پیامک استاد و دسترسی — ۱۷، ۱۸

روشن کردن رویداد: «کار آماده / قبل از تحویل به مشتری» جدا از تحویل نهایی.  
تنظیم کسب‌وکار + **مجوز/انتخاب عضو**: چه کسانی SMS بگیرند (استاد، مسئول پرونده، لیست اعضا).  
رفع باگ ارسال‌نشدن روی CASE واقعی (لاگ + تست).  
**تست:** بدون مجوز نگیرد؛ با مجوز بگیرد؛ قطع اعتبار → صف ب.

**فاز ۱ این نوبت:** باگ برند/مدل آزاد + پیش‌فرض انجام‌دهنده = مسئول پرونده + نظرسنجی مشتری یک‌صفحه‌ای (بدون auto-advance). صف SMS، ساعت کارکرد، پذیرش چهارمرحله‌ای، چندقلم محصول → فازهای ۲–۴.
